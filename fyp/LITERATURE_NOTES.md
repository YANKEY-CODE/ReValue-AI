# Literature-review research notes

These are working notes for the student's own literature review. Separate peer-reviewed publications from vendor documentation and official evaluation code. Repository descriptions establish what assets and licences the project reports; they do not establish that a reported accuracy claim transfers to ReValue.

| Source | What to extract for the review | ReValue interpretation and limit |
| --- | --- | --- |
| Schaub et al., *Broken Display = Broken Interface? The Impact of Display Damage on Smartphone Interaction*, CHI 2014. [DOI](https://doi.org/10.1145/2556288.2557067) · [Released dataset and terms](https://github.com/MHCI/broken-interfaces) | Motivation for considering visible smartphone display damage and for studying whether it relates to interaction. The source repository describes photographed displays and manual SVG damage annotations. | The six display crops contribute qualitative stress examples. Their annotations and capture provenance are not a verified two-class, device-disjoint holdout for ReValue. Cite the authors and CC BY 4.0 terms if using the material. |
| Han et al., *SSGD: A Smartphone Screen Glass Dataset for Defect Detection*, ICASSP 2023. [Authors' repository and citation](https://github.com/VincentHancoder/SSGD) | An example of a seven-class screen-glass detection taxonomy and a cross-validation protocol. Compare the semantics of crack and scratch to ReValue. | Screen glass is narrower than whole-device assessment. The checked-in configuration reuses each validation fold as its test fold. The archives weren't accessible, so don't assert split integrity or cross-domain transfer. Dataset reuse is described as academic-only. |
| Ultralytics, [YOLO11 technical documentation](https://github.com/ultralytics/ultralytics/blob/main/docs/en/models/yolo11.md) | Describe the model family, nano/small variants, detector outputs and deployability trade-off. This is product documentation. | ReValue pins its verified nano weights; the separate Houdan asset is empirically a small variant. Neither published COCO performance nor an upstream project's numbers measure this application. |
| COCO project, [official detection evaluation implementation](https://github.com/cocodataset/cocoapi/blob/master/PythonAPI/pycocotools/cocoeval.py) | Explain intersection over union (IoU) and AP across multiple IoU thresholds. Discuss the difference between an operating-point precision/recall result and AP over ranked detections. | The planned common-class evaluation separates AP@50, AP@50–95 and fixed-threshold errors. These metrics are deferred because a verified independent test set is unavailable. |

Suggested discussion order: smartphone exterior damage and user consequences, object detection and annotation choices, device/session independence and metrics, then resale decision support. In the last section, explain the difference between a listing observation and a transaction, why results depend on comparable condition, and why user-entered offers and repair quotes are kept separate from model scores. The checked notes do not support a claim about market-wide resale accuracy.

Use [the system handoff](FYP1_SYSTEM_HANDOFF.md) for design requirements and verified implementation evidence. Where a source is represented only by its repository description, read the full paper before citing findings beyond that description.
